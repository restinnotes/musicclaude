# B. 面向新作品的生产 DAG（到 Bead / STRUCT 为止）

> 这是从本轮实验里留下来的、明天输入一首新作品时真正要重复执行的流程。实验中为找方法而跑的东西（语义增益曲线、一次调用对照组、Pool 消融、三方盲评、精简复核）**不在**这里。

## 1. 明天输入一首新作品，系统依次做什么

```
① 独立发表的音乐结构资料 ──► 冻结分段（S01…Sn，含小节范围）            【沿用，不在本轮范围】
② 多模型多轮 A 研究（无 Muse；不加入 Gemini Pro / Grok / Opus / 旧 Sol） 【沿用，不在本轮范围】
③ Pool：每段一次调用，按音乐位置归集原文                                  【保留，职责收窄】
④ 精选：每段，会话 G 第 1 轮 —— 按边际价值排序的侧面阶梯 + 停止点         【新】
⑤ 独立核查：每段，会话 R 两轮 —— 先盲列体验清单，再逐个审阶梯            【新，取代旧 audit】
⑥ 定稿：每段，回到会话 G 第 2 轮 —— 核对审稿，写出 Bead / STRUCT          【新，取代旧 synth】
⑦ 整曲检查：全曲一次 —— 只查跨段模板与段界衔接；被点名的段回会话 G 修订  【保留为一次调用】
                                                         └──► Thread（本轮不做）
```

段与段之间完全独立，③④⑤ 可以同时开跑（⑤ 的第 1 轮不依赖 ④）；同一段内 ④→⑤第 2 轮→⑥ 按依赖顺序。⑦ 等所有段完成后跑一次。

脚本（不调用模型、不改写文字）负责：逐字引文核验（对原始 A）、小节是否落在本段、模型身份与 max / Temporary / Unpersonalized 校验、缓存与恢复、拼接交付。

### 每一步的真实职责

| 步骤 | 输入 | 输出 | 职责 |
|---|---|---|---|
| ③ Pool | 本段小节范围 + 全部 A | 每份原稿对本段说了什么：逐字原话、原稿范围→判断后的小节、一句复述；邻段排除 | **检索与溯源的数据层**。记录"原稿说的是哪里、为什么判断在这里"，供 ④ 当索引、供以后人工追查。它不是内容清单，不追求覆盖。 |
| ④ 精选（G1） | 本段 Pool + 全部 A 附件 | 侧面阶梯：第 1 个＝只能给一个时最值得给的；第 k 个＝在前面基础上新增最多的；每个带原文依据、并入的其他说法、与前面的关系、建议停止点、明确不用的材料及理由 | **轻度二次理解在这里完成**：比较材料的共同点与差别，同义比喻并入一条，判断六类关系。共同道理只写进 internal_note，不替代画面。 |
| ⑤ 独立核查（R1→R2） | R1：只有 A 和小节范围；R2：匿名阶梯（不含生成者的增益等级与停止点） | R1：审稿者自己的本段体验清单；R2：逐个判断真正新增了什么、关系是否标对、位置、拼接、抽象化、值不值得注意力；遗漏线索 | **找生成者自己看不到的问题**：错排的尾部、被误判为二选一的并存体验、被压成静态的段内变化、跨来源拼接。先盲列再看稿，保证它不是在确认生成者的判断。 |
| ⑥ 定稿（G2） | 审稿意见原文 | 最终 Bead / STRUCT ＋ 读者正文 | 回原稿逐条决定采纳与否；**审稿的"补入/多保留"只当线索**，优先压成半句并入已有条目；条目数与正文与段落时长相称。 |
| ⑦ 整曲检查 | 全部定稿 + A | 哪些段被跨段模板挤掉了本段体验；段界衔接 | 一首作品只跑一次；只修被点名的段（本轮 14 段中 3 段）。 |

### 最终 STRUCT（⑥ 的输出）长什么样

每段一个 JSON（实例见 `struct/Sxx.json`）：

- `beads`：精选后的体验，每条有自然中文 `text`、`role`（主体验／另一侧面／另一种理解／段内变化／演奏条件）、`measures` 与 `placement`、`performance_condition`、逐字 `sources`、`also_expressed_by`（并入的其他鲜活说法，呈现时可替换）、`vivid_lines`（可直接上屏的原句）。
- `relations`：只写真实存在的关系（可同时成立／另一种理解／段内先后／重叠但新增）。
- `timeline`：只有段内确有先后变化时才有。
- `reader`：给听者的连续正文，只用 beads 内容，可以不全用；`reader_uses` 标出用了哪些。
- `stop_reason`、`not_kept`、`review_responses`、`internal_note`。

不再有几百条独立 facet / reading / ledger / carryover。不同表达共享一个体验条目（`also_expressed_by`），不再各自成为条目。

## 2. 和上一轮链路相比：保留、合并、删除

| 旧环节 | 处理 | 依据 |
|---|---|---|
| Pool（pool_v2） | **保留，职责收窄**为检索/溯源/位置判断的数据层 | 一次调用条件下的消融（4 段）未发现把 Pool 当输入能改善内容（nopool 3/4 段胜过有 Pool 的一次调用）；但它记录的"原稿范围→判断"是位置判断的可追查依据，生成阶段排除的 155 条邻段/错位材料都靠它定位。复用即可，不需要更细。 |
| synth_v4（Pool→STRUCT，要求每条 Pool 都有去向） | **删除**，由 ④＋⑥ 取代 | 旧 synth 以账本完整为目标，产出 589 facets / 226 readings；本轮以边际价值为目标，14 段共 62 条，盲评中阶梯＋审稿＋修订优于一次调用（cmp2 平均名次 1.57 vs 2.43）。 |
| ledger（每条 Pool 的去向） | **删除**，改为 ④ 的分组 `set_aside` | 逐条账本只服务覆盖指标；分组理由（重复／邻段／抽象／无依据）已足够追查。 |
| audit_v1（打覆盖率、可读性分） | **删除**，由 ⑤ 取代 | 旧 audit 只产出分数，不进入内容；⑤ 的意见直接进入 ⑥ 并被逐条回应。 |
| display 阶段（disp1，STRUCT→展示稿） | **删除**（合并进 ⑥ 的 `reader`） | 读者正文与 STRUCT 同一次调用产出，不需要第二次综合。 |
| `short_beads_ref.json` 作为写作参考 | **删除** | 受 Muse 素材影响；本轮完全不用它，质量未受损。 |
| 整曲检查 | **保留为一次调用** | 本轮它找到 S08 的模板挤占和 S13→S14 的段界遗漏，且没有误伤有原稿依据的重复。 |
| 语义增益曲线、一次调用对照、Pool 消融、三方盲评、精简复核 | **不进入生产** | 这些是找方法的实验。 |

为什么不是一次调用：两轮独立盲评中，一次调用（无论是否加入实验学到的规则）都输给"阶梯→审稿→修订"；单次调用压篇幅时先丢失的是具体画面（prod2 鲜活度多为 4 分）。为什么不是更多步：本轮里每个保留的步骤都改动了实际内容（审稿 162 条意见中 161 条被采纳或部分采纳；两轮整曲检查分别点名并修订了 3 段和 4 段），没有只产出分数的步骤。

## 3. 本轮发现的失效模式，以及生产版提示词的改动

修订会话几乎全盘接受审稿（只拒绝 1 条），而审稿建议保留数平均比生成者多 1.5 条，结果 4 段过载（S10 达 8 条），盲评输给一次调用。生产版的定稿提示词（`prompts/final_v2.md`）因此加了两条：

- 审稿的"补入/多保留"先尝试压成半句并入已有条目；只有值得在本段时长里再占一次注意力时才另立一条；遗漏是线索，不是必须逐条落实的清单。
- 条目数与正文与本段时长相称；同一音乐动作的几种画面写成一条里的对照。

**验证**：用 final_v2 在全新会话里把 ③④⑤⑥ 完整跑了 14 段（`gen_b → rev1_b → rev2_b → final_b`），与第一次实验的 final 和一次调用版 prod 三方盲评：

| | 平均名次 | 第一名段数 | 被评"注意力合适"的段数 |
|---|---|---|---|
| 生产链路 final_b | **1.43** | **9** | 13 |
| 实验链路 final（旧定稿提示词） | 2.00 | 4 | 6 |
| 一次调用 prod | 2.57 | 1 | 3 |

先跑的 5 段（含过载最严重的 S05、S06、S10）final_b 全部第一；后跑的 9 段赢 4 段，另 4 段输给第一次采样的 final。所以：final_v2 消除了过载、整体最好，但同一流程两次采样之间仍有可见的波动，单次产出并不保证每段都是最好的一版。

## 4. 成本与吞吐（按本轮实测）

- 每段 5 次模型调用（Pool 1、G 两轮、R 两轮），全曲另加整曲检查 1 次和少量针对性修订（本轮 2–4 段）。14 段约 75 次。
- 实测单次耗时中位数（生产链路这一轮）：G1 约 7 分钟、R1 约 7.5 分钟、R2 约 4.5 分钟、G2 约 4.5 分钟；Pool 约 10 分钟（上一轮记录）；整曲检查约 8 分钟。并发 16–20 时没有观察到变慢或失败。
- 按依赖关系，全曲约 4 个波次，16–20 路并发下墙钟约 35–45 分钟（不含 Pool 时约 25–30 分钟）。

## 5. 运行方式

当前实现：`D:\musicclaude\_bead_saturation_20261018\sat.py`。它同时包含实验阶段；生产只用下面这几个（`_b` 后缀的阶段就是经过验证的生产链路，定稿用 `prompts/final_v2.md`）：

```powershell
python sat.py run --stages gen_b,rev1_b,rev2_b,final_b --segs all
python sat.py piece --stages final_b
python sat.py run --stages final2_b --segs <整曲检查点名的段>
```

③ Pool 沿用上一轮链路（`bead_chain/chain.py pool`，提示词 `pool_v2.md`），本轮直接复用了其产物。新作品接入时需要改的只有：`inputs/A/`（新作品的 A 原稿）、`inputs/structure.json`（冻结分段）、`inputs/pool/`、以及提示词里的作品名；`SEC_PER_MEASURE` 按作品时长与小节数估计。

- 并发数从 `runs/parallel.txt` 实时读取，可在运行中调整；同账号相邻提交间隔 6 秒。
- 成功的步骤以 `parsed.json` 缓存，重跑不会重做。
- 调用失败时，若证据目录显示请求**已提交**，标记为 `uncertain` 且不自动重发（防止重复提交）；只有提交前失败才等待后重试一次。
- 每次成功调用都检查实际模型为 `gpt-6-thinking`、`max`、Temporary、Unpersonalized，不符即判失败。
