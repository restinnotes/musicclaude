# 实验、评价和归因合同（给 Claude 决策、Muse 执行）

## 1. 所有重大比较必须定义对照

对每个假设先写五句话：

- **问题**：哪一类真实听者体验不够好？给出具体出处/小节/原句。
- **可证伪假设**：究竟是什么机制导致问题？若错了会看到什么？
- **单变量**：本轮只变模型、prompt 一处、输入权限、某个筛选 gate 或架构的一层，其余固定；混合改变只能另作探索，不能作因果结论。
- **盲比参照**：配对同输入同篇幅，另附跨版本原始 V2A+Gemini（reference 02/05）基线 + 当前 production；找不到对应稿就标缺失。
- **采取行动的证据**：什么样的质量变化能让我们采用，什么失败需要回滚；不要后见地改指标。

## 2. 多模型比较

- 同一任务角色比较 GPT-6 / GPT-5.6，所有外部网页 GPT 经本机 `gpt2 --help` 实测后的 CLI 适配器；用最新实际模型标识、档位、路由、时间、hash，**不要凭客户端名称声称真实后端型号或推理深度**。
- 初轮不得一边换模型一边改 prompt/架构；默认新鲜配对、独立会话、尽可能相同的字数/输出预算和相同内容时间边界。
- 对 BEAD 统计 A 核心保留、未支持新增、未来信息泄漏、近义重复，重点报告**单位阅读负担下的独特有效内容**。历史 52%→89% 覆盖差异受新文本更长混杂，不可当纯模型提升。
- 对 E5/History/Thread 重点评估“所增加的关系是否值得告诉听者”；NONE/NO CHANGE 必须合法，不拿输出比例作为单一质量目标。
- 对 Center/全曲叙事同时保留有根据的鲜明解释及真实竞争解释；不要把“深情、坚定、戏剧、单故事”一概扣分。
- 对 E7 比较顺音乐阅读的实际连贯性与信息负担，历史稿/新稿匿名化；不是更短或更长自动更好。

## 3. 评审用统一禁偏见条款（必须写进每份 judge prompt）

> 请只根据音乐文本中可辨的时间/材料依据、独特有效的听者体验、信息增量、具体性、前缀诚实、语义保真、作品特异性和实际阅读效果裁判。**戏剧化、笃定、因果写得很满、单一情感故事本身均不扣分**；只有缺证据、与素材矛盾、压掉关键独立解释或重复灌水时才扣分。NONE/NO CHANGE 可能是正确答案，但不为了追求空白而删有价值的信息。每项裁决必须引证双方原文及支持/反例，遇证据不足明确说不可判。不要根据模型名称或上游自述评分。

此段可以由 Muse 放进所有评审提示词的共同版本；生产生成 prompt 严禁夹入作品专属用例/标准答案。

## 4. 独立评审流程

1. Muse 匿名化候选顺序、记录盲审随机种子、材料来源 ID、输入版本；不能让 judge 看见生成者身份。
2. 统计（时间/字符数/重复/条目覆盖/哈希）全部用脚本算；不要让模型估计数字。Muse 审核统计输出到原始输入可复查。
3. 免费 Muse 可大量挖例、分别找优点/反例、挑出最能翻转结论的句对；Claude 每个关键决策亲读少量代表性样本并必要时扩大。
4. 重大质量判决至少一名与候选生成分离的评审模型；有争议时增加异构评审（如 Opus/其他已授权模型），而不是对同一个模型重复问“你确定吗”。
5. 必须记录**分歧**：哪种证据让两个 judge 互相矛盾、用户北极星对其怎样裁决、是否需要真实聆听核对。不要用平均分掩盖作品理解差异。
6. 不允许主 Claude 亲自产出一份参赛整篇候选，再用自身评审其胜利。可以由独立 Opus/GPT/Muse 生成候选，由 Claude 裁决。

## 5. 降级/异常速度核查

每次请求保留：route+CLI版本、requested/reported model（如果可见）、effort（如果可见）、开始结束时间、elapsed、输入/输出 token 或长度、文件/提示词/输出 sha256、返回码、错误输出、安全的请求元数据、运行 ID、cache_key/hash。不能保存 credentials/cookies。

- 几十秒产出几千字符、答非所问、聚类过粗、健康探针错误等属于**异常信号**，不是降级定论。
- 对可疑输出：标注 `suspect`、隔离从正式比较中剔除、在健康通道做相同输入与 prompt 的成对复测；隔离原始文件不删除。
- 若某轮新结果读取 10-05 旧 `archive_gpt56w_1005` 等历史缓存，先定位生产和消费链，排除污染，再决定是否局部重跑。
- 10-05 旧 run126 部分可疑结果按旧状态处理；10-06 `v2_1006` 重新生成的 H1–H5/CANON/RESID 以及新的 manifest 不应无证据地全盘作废。
- 不断尝试水杯题、频繁健康探针不是核心目标；最应验证的是**实际音乐任务输出质量**与路由证据。未经授权不做规避服务风控的动作。

## 6. 可复现归档与阶段验收

每次实验固定 `run_id`、source commit、input set、prompt 文件与版本、唯一改变点、模型/档位、路由、随机条件、结果路径、裁决证据与未解决分歧。脚本产生 manifest 和 hash。旧 run 只读，新 run 不覆盖老数据。

格式建议：

```text
runs/<run_id>/
  experiment.md                 # 问题、假设、对照、评判、决定
  manifest.json                 # commit / producer / model / hash / elapsed
  inputs/                        # 或带 hash 的指向原始材料的索引
  outputs/                       # 原文
  blinded/                       # 匿名 A/B 测试材料与种子
  eval.json                      # 可复查原句的维度评审
  failure_cases.md               # 关键反例及对应原文位置
  report.md                      # 结论、局限与采取行动
```

只有原任务 `06_ACCEPTANCE_CRITERIA.md` 逐条已被证明，且三首作品与原始基线对照真实有效，才可声明 **production ready**。若验收条文与用户最新目标出现实质冲突，提出证据和拟修订条款，请用户授权，不得自行把失败改名通过。
