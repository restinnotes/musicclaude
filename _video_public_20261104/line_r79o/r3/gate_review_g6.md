# 一、结论：现在的迭代函数不合格，不能保证做出你们要的东西

问题不是简单地少了几个指标，而是**现在优化的对象和你们真正想要的成品，已经出现了系统性偏差。**

我认为有六个最严重的问题：

1. **把 w23 当成所有指标的合格线，是根本性的基准错误。** w23 已经被用户否定，不能用一个已知不符合目标的版本定义什么叫合格。
2. **没有事实忠实性硬门槛。** 最近已经出现疑问改断言、加入定稿没有的话，迭代函数却放行。这是已被实测证明的漏洞。
3. **没有独立的核心内容保护机制。** 用户要求先独立排序，再检查最核心的有没有丢，现在只有总体覆盖率。
4. **没有真正测扫读。** GPT 看文字、看到停留秒数，不等于它真的在这几秒内扫过了视频。
5. **线的四项要求没有被直接测量。** 压缩、异质性、独立性、与珠子的关联，是用户明确要求直接测的，现在主要只有一个人话分数。
6. **没有端到端测视觉和音乐。** 动画、颜色、局部小节、高音对应、珠线混合，都不能靠文字盲比验收。

另外，11-08 的新要求尤其重要：

**RHP 目前仍然是把珠子和线分成两种东西，再交替展示。它不是用户要的揉在一起。**

我不建议现在直接用你写好的提示词开跑。应该先修迭代函数，再修写稿提示词，否则模型很可能非常努力地优化错误的目标。

# 二、逐条体检：15 条标准在不在迭代函数里？

标记说明：

- <badge color="success">基本覆盖</badge> 已有对应指标。
- <badge color="warning">部分覆盖</badge> 有相关指标，但测量不完整。
- <badge color="danger">缺失</badge> 没有真正进入优化目标。
- <badge color="danger">测量方向错误</badge> 有指标，但容易优化出与用户意思相反的结果。

| 标准 | 现在是否覆盖 | 具体问题 |
|---|---|---|
| 1. 扫一眼就抓到 | <badge color="warning">部分覆盖</badge> | 盲比测了扫得动、抓要点，但没有真实时间压力。 |
| 2. 珠子被线串起来 | <badge color="warning">部分覆盖</badge> | `why`、`whole` 间接涉及，但没有直接测珠子和线的匹配关系。RHP 仍然分开。 |
| 3. 珠子讲当下体验 | <badge color="warning">部分覆盖</badge> | 珠子覆盖能测具体内容是否留下，但没有直接测成品是否偏向音乐描述而非人的体验。 |
| 4. 很短但内容够 | <badge color="danger">测量方向错误</badge> | 盲比能间接测短和理解，但没有真实扫读；写稿提示词还用 w23 字数比例限制。 |
| 5. 不妨碍理解、不制造时序 | <badge color="danger">缺失</badge> | 没有独立测同段并列内容是否被误解为先后。强制因果同句还可能制造不存在的关系。 |
| 6. 最核心的不能掉 | <badge color="danger">缺失</badge> | 没有独立排序，也没有加权覆盖。普通覆盖率可能掩盖核心内容丢失。 |
| 7. 局部内容有动画 | <badge color="danger">缺失</badge> | 写稿可以输出 bars，但迭代函数没有检查最终动画是否按小节出现、是否同步。 |
| 8. 可以引导阅读顺序 | <badge color="warning">部分覆盖</badge> | 扫得动可能间接反映，但没有测观众实际先看什么、是否因此理解正确。 |
| 9. 不编 | <badge color="danger">缺失</badge> | 写稿提示词要求不编，但没有独立的事实忠实性硬门槛。已经出现过实际漏检。 |
| 10. 珠子相关质量不能比定稿线差 | <badge color="warning">部分覆盖</badge> | N09 只测线人话，不能代表简短、独立、连贯、人话等全部要求。珠子覆盖还被过度强调。 |
| 11. 说得直接 | <badge color="warning">部分覆盖</badge> | 有 N09 和整屏人话，但 N09 提示词没有提供，无法验证；整屏只卡严重问题，容易放过大量不自然的中等问题。 |
| 12. 一屏里看得出异质 | <badge color="danger">缺失</badge> | 没有直接评估不同性质的组是否真的不同，以及匹配的珠子是否体现了区别。 |
| 13. 颜色本身带情绪 | <badge color="danger">缺失</badge> | 写稿提示词只有连贯行的 emotion，没有检查珠子颜色、全曲颜色一致性、音乐图颜色。 |
| 14. 文字和音乐图对应 | <badge color="danger">缺失</badge> | 没有把文字、音符数据、可视化编码、最终画面放在一起验收。 |
| 15. 珠子散开，线接得上 | <badge color="danger">测量方向错误</badge> | `whole` 只能间接测理解；没有检查视觉上是否真正融合，也没有测珠子散开程度。 |

这里还有一个容易忽略的问题：

**标准 #10 中的“不倒退”不是所有指标都必须达到定稿线的覆盖程度。**

用户明确说过，覆盖可以放宽，不要求每颗珠子都接上。但人话、压缩、连贯、独立这些不能倒退。

现在的函数把不同性质的要求混在了一起：

- 覆盖：有单独指标。
- 人话：有单独指标。
- 压缩：没有真正单独指标。
- 独立：没有真正单独指标。
- 连贯：盲比间接判断。
- 与珠子关联：没有真正单独指标。

因此，即使这几个已有分数全部通过，也不能说明线已经达到要求。

# 四、最重要的基准问题：w23 不能再当目标函数的基准

这是我建议第一时间改的地方。

现在的逻辑是：

\[
新版质量 \geq w23质量
\]

然后：

- 盲比不比 w23 差；
- 原稿覆盖不低于 w23；
- 珠子严格覆盖不低于 w23；
- 精细体验不低于 w23；
- 整屏严重人话问题不多于 w23。

这有一个逻辑错误：

**你们已经知道 w23 有一些不符合目标的地方，却把它作为新版本的最低合格标准。**

这会造成三种问题。

### 1. 继承已知错误

假设 w23 有：

- 线珠分开；
- 阅读顺序不理想；
- 珠子不够碎；
- 局部动画不明显；
- 文字没有真正压缩；
- 某些感受不够细腻。

那么新版本只要不比它差，就可能通过。

甚至新版本可以保留这些问题，只要别的维度得分够高。

### 2. 指标允许错误的优化方向

例如：

为了提高珠子覆盖率，模型把所有珠子都放回去。

结果：

- 覆盖率上升；
- 屏幕变得拥挤；
- 扫读变差；
- 观众抓不到重点。

它却可能通过覆盖门槛。

### 3. 没有真正的绝对合格标准

一个版本可以在所有指标上不比 w23 差，但仍然只有 50 分。

这不是你们要的七八十分大众版。

## 正确做法

把基准分成三类：

| 基准 | 用途 | 是否作为硬门槛 |
|---|---|---|
| 原始珠子+线定稿 | 内容真实性、覆盖、核心排序 | 是 |
| 人工确认的优质正例 | 人话、扫读、异质、融合等目标质量 | 是 |
| w23 | 历史回归参照，了解新版本有没有退步 | 否，不能单独决定合格 |

特别是 w23 的盲比：

可以继续记录，但不能因为它赢了或没输，就认定新版本合格。

**目标应该是达到独立定义的质量标准，而不是打败一个已被否定的旧版本。**

# 五、优先修复的十个问题

下面按重要性排序。每项都给出测量、门槛和校准方法。

## P0-1：增加事实忠实性和不编造硬门槛

<badge color="danger">最高优先级</badge>

这是现在已经出现过实际漏洞的地方。

已发生的问题：

- 疑问句改成断言；
- 添加定稿没有的内容；
- 修改原本的语气；
- 为了连贯而改变意思。

现在写稿提示词有“不改意思”，但没有对应的独立评审门槛。

**怎么测**

增加一个专门的忠实性评委。

关键提示词：

```text
你是内容忠实性审查员。

对照原始定稿的珠子和线，逐条检查屏幕上的所有文字。
不要只检查大字，也要检查小字、散落短语和融合后的句子。

对每个屏幕表达，判断：

1. 能否在原稿中找到明确依据？
2. 是否增加了原稿没有的事件、人物行为、画面或情节？
3. 是否把疑问改成了断言？
4. 是否把猜测、担心、可能改成了确定事实？
5. 是否把心理比喻变成真实发生的事件？
6. 是否添加了原稿没有的因果关系？
7. 是否改变了原稿中并列内容的时间关系？

逐条给出：
忠实 / 语气或关系改变 / 无依据新增。

必须指出对应原稿和屏幕稿的位置。
```

**怎么卡**

硬门槛：

- 不允许新增实质性事件；
- 不允许疑问变断言；
- 不允许猜测变事实；
- 不允许无依据地增加因果和时间关系；
- 不允许把比喻变成真实事件。

一处实质性错误就退回修改。

不能让其他分数补偿这个错误。

**怎么校准**

用已有材料人工造正反例：

| 正例 | 反例 |
|---|---|
| 会不会也舍不得结束这份亲近？ | 对方也舍不得结束这份亲近。 |
| 他怕对方嫌自己太黏 | 对方嫌他太黏。 |
| 话卡在唇边 | 他最终没有说出这句话（如果原稿没有明确说明） |

评委必须能稳定区分。

这项应当放进快筛，而不是等所有评审跑完才发现。

## P0-2：增加独立核心排序和加权覆盖

<badge color="danger">最高优先级</badge>

用户很早就说过：

> 把最核心的关键点不能掉，就是从主要到次要比如一个独立的去排序，然后和现在做出来的东西进行对照。

现在的覆盖率不等于核心保护。

举个例子：

原稿有：

- 一个最核心的转折；
- 两个重要的心理变化；
- 十个辅助感受。

新版本丢掉最核心的转折，却留下十个辅助感受。

普通覆盖率仍然可能很高。

**怎么测**

在写稿前，独立评委先对原始珠子+线做核心排序。

至少分成：

- 核心；
- 重要；
- 辅助。

注意：排序必须在看到屏幕稿之前完成，最好由独立评委完成，不能让写稿模型自己定义什么重要。

然后对屏幕稿检查：

1. 核心内容是否保留；
2. 重要内容保留多少；
3. 辅助内容保留多少；
4. 是否保留了原稿中最关键的转折和解释关系。

**怎么卡**

- 核心内容：硬门槛，不允许丢失实质意义。
- 重要内容：设独立覆盖门槛。
- 辅助内容：记录覆盖率，不要求全部保留。

不要用一个总覆盖率掩盖核心遗漏。

**怎么校准**

人为制作两种版本：

- A：保留核心，删掉一部分辅助内容。
- B：保留大量辅助内容，但删除最核心的转折。

评委必须明确认为 A 更符合目标。

如果评委分不出来，核心排序机制就没有校准成功。

## P0-3：把扫读从文字判断改成真实时间测试

<badge color="danger">最高优先级</badge>

目前盲比提示词有一个根本问题：

它说观众边听音乐边扫，但评委实际上只看到了文字。

它没有：

- 真正听音乐；
- 真正看到动画；
- 真正经历停留时间；
- 真正受到扫读注意力限制。

所以它只能判断文字看起来是否容易扫，不能证明实际扫得动。

**怎么测**

用最终渲染的视频做测试。

找没有看过原稿的普通读者：

- 视频正常播放；
- 不暂停；
- 不回看；
- 不提前给原稿；
- 每段结束后，快速回答两个问题：

1. 刚才这一段是什么感受？
2. 这个人现在为什么是这样？

再让读者复述他抓到的主要关键词。

关键不是要求他读完所有字，而是：

**他只抓到一部分时，能不能抓到正确的东西。**

可以同时保留 GPT 盲评，但 GPT 不能代替这个测试。

**怎么卡**

- 核心感受必须能被抓到；
- 人物此刻的处境和原因不能在关键段落丢失；
- 不能依靠暂停、回看、全文阅读才能理解；
- 个别辅助珠子没被看到可以接受。

不要使用统一字数比例代替这个测试。

**怎么校准**

准备三种已知不同的版本：

1. 人工认可的可扫版本；
2. 故意堆很多字的过密版本；
3. 过度压缩、看不懂的版本。

实际读者必须能稳定区分。

这项还可以反过来校准每段到底能放多少内容，而不是先规定一个字数，再让写稿模型硬凑。

## P0-4：珠子覆盖必须改成整屏内容覆盖，同时测具体体验

现在珠子严格覆盖提示词有一个特别严重的问题：

> 只看小字感受。

这在珠子和线揉在一起以后已经不成立了。

假设：

原稿珠子：

> 脚下没了支撑。

新屏幕稿：

> 他没藏住喜欢，脚下没了支撑。

这个具体感受明明还在，却因为出现在大字句子里而不算覆盖。

这是指标定义和新设计直接冲突。

**怎么测**

修改珠子覆盖评委：

```text
检查原稿中的每一颗珠子，在整个屏幕稿中是否保留。

注意：
不区分大字、小字、连贯句、散落短语。
只要屏幕上保留了该珠子的具体含义，就可以算覆盖。

但必须区分：

留住：具体画面、身体感觉、比喻、心里话、转折仍然存在。
部分：只留下大意或情绪，具体体验消失。
没有：找不到对应内容。

另外独立判断：
屏幕稿是否仍然以人的当下体验为重点，
还是退化成了对音乐本身的描述。
```

**怎么卡**

- 高优先级的具体体验不能丢；
- 整体珠子覆盖率设独立目标；
- 低优先级珠子允许舍弃；
- 不要求每颗珠子无条件出现；
- 不能用叙事中出现的泛泛情绪，冒充具体珠子覆盖。

**怎么校准**

例如：

| 原始珠子 | 屏幕内容 | 正确判定 |
|---|---|---|
| 脚下没了支撑 | 脚下没了支撑 | 留住 |
| 脚下没了支撑 | 心里不安 | 部分 |
| 脚下没了支撑 | 他有点孤单 | 没有 |
| 脚下没了支撑 | 他没藏住喜欢，脚下没了支撑 | 留住 |

最后一例特别重要：必须确认评委不会因为珠子被揉进叙事句就漏判。

## P0-5：把线的四个指标真正拆开测

<badge color="danger">最高优先级</badge>

11-05 用户明确提出：

> 线要真的压，同时要异质、压缩、独立、和珠子关联，要直接测这四项。

现在主要依赖 N09 人话评审。

这是不够的。

我建议四项分别评估，不能合成一个总分。

| 指标 | 怎么测 | 硬门槛 |
|---|---|---|
| 压缩 | 和定稿线逐条比较，判断是否去掉重复、次要细节，同时保住因果和必要解释；结合实际停留时间 | 不能只是复制原稿，也不能压到因果断裂 |
| 异质 | 对照原稿各组的性质，检查不同组是否保留不同的内容功能、情绪和表达 | 核心异质组不能被合并成同一种情绪或同义词 |
| 独立 | 把每条线单独拿出来，不给上下文，让评委判断能否理解人物、事情和意思 | 关键线不能依靠上一条才能猜懂 |
| 与珠子关联 | 对照原稿已有匹配，判断观众能否感到珠子属于这个人的处境 | 不能只靠颜色相同或情绪相似来冒充关联 |

**校准方法**

分别造反例：

- 压缩反例：完全不压，照抄定稿线。
- 过度压缩反例：只剩几个抽象词，因果没了。
- 异质反例：把不同组都改成“不安、失落、难过”。
- 独立性反例：单独拿出来没有主语和指代依据。
- 关联反例：随机把珠子分配给不同的线。

正例则用原始匹配关系，保留不同性质和必要上下文的版本。

每项单独过门槛，不能靠其他项的高分抵消。

还有一个审计限制：N09 的完整提示词没有附上，所以我现在不能确认它到底有没有覆盖这些问题。但从你描述的当前函数看，不能认为四项已经被测到了。

## P0-6：增加 Center 关联和 DFS 深入程度

这是 11-06 明确提出、现在完全缺失的指标。

**怎么测**

给评委三份材料：

1. 全曲 Center；
2. 每段原始定稿线；
3. 当前屏幕稿。

要求评委判断：

- 每段线与 Center 有什么关系；
- 每段是否在沿着某一条核心脉络深入；
- 是否在推进一个问题、一个关系或一个心理状态；
- 有没有无依据地跳到另一个分支；
- 有没有来回重复探索、走成迷宫；
- 每段的落点是否为后续内容提供了依据。

这里不要求每段都重复 Center 的关键词。

要求的是：**整条线在语义上始终服务于 Center。**

**怎么卡**

- 核心段落必须能解释其与 Center 的关系；
- 不能出现重大无关支线；
- 不能为了让每段都看起来连贯而制造回头、重复、绕圈；
- 深入可以有停顿，但必须有依据。

**怎么校准**

用同一套材料造两版：

- 一版按 DFS 顺序深入；
- 一版故意把不同分支交错排列，反复回头。

评委应该能明显区分。

这项不能从 `前后是一件事` 推断出来。前后是一件事，不代表它在正确地深入。

## P0-7：增加珠线融合、非时序理解和阅读路径评审

这是 11-08 的核心新要求。

**怎么测**

让评委看到实际渲染的一整段屏幕，而不是给它标注哪些是珠子、哪些是线。

测三个问题：

1. 观众是否觉得这是同一个人的事情和感受，而不是两个栏目？
2. 同段的并列感受是否被理解为并列，而不是依次发生？
3. 观众是否自然知道先看哪里，随后怎么把不同内容联系起来？

**怎么卡**

- 不允许出现明显的来源分栏、来源分区；
- 不允许把并列关系误导成时间顺序；
- 阅读路径应该有引导，但不能强制观众按一条虚构的故事顺序理解；
- 连贯、散落、混合三种形态都允许。

**怎么校准**

至少拿三种版本：

- RHP 当前这种明确分开的版本；
- 真正混合的版本；
- 故意把并列内容做成时间先后的版本。

评委必须能识别第一版的问题和第三版的误导。

## P1-8：整屏人话不能只卡严重问题数量

当前：

> 严重问题条数不多于 w23，中等问题只记录。

这会导致一个很容易发生的问题：

每一行都有一点书面腔、提纲感、硬切感，但每一行都不算严重，最后整屏还是不像人话。

11-05 用户已经明确指出：

- 感受压成书面短语不是人话；
- 把一句话硬切成几块也不是人话；
- 句式需要多变。

**怎么测**

对大字、小字、碎片和整屏分别评审：

```text
判断这些文字是否像一个普通人自然地讲述自己的经历。

重点检查：
1. 是否像提纲，而不是自然表达。
2. 是否为了短而把一句话硬切成没有自然关系的片段。
3. 是否使用不自然的书面短语。
4. 相邻句式是否机械重复。
5. 是否存在格言、心理分析、空泛总结。
6. 短语和感叹是否自然、直接、一扫能懂。

允许不完整陈述句。
不允许用不自然的书面短语冒充碎片化。
```

**怎么卡**

- 严重人话问题：硬门槛；
- 同类中等问题反复出现：也要退回；
- 不能只统计严重问题总数；
- 人话质量不低于人工认可的线稿。

**怎么校准**

使用 11-05 已被用户否定的截图或对应文字作为负例。

尤其要造两种反例：

- 一句完整但很书面的句子；
- 把完整句子硬切成多个看似很短的书面短语。

评委都应该识别为不合格。

## P1-9：增加真正的视觉、动画和音乐对应验收

目前的迭代函数基本没有这一层。

但用户标准里有大量内容不是文字本身能够证明的。

建议单独做一个渲染评审。

**测量项目**

| 项目 | 验收内容 |
|---|---|
| 布局 | 上字下图，音乐动画在中央，符合指定实现 |
| 线 | bullet 形态，组与组有清晰的实心底色 |
| 珠子 | 不要背景，散落而不是挤成完整句子 |
| 交界 | 共享词块贴着两组接缝，颜色渐变 |
| 颜色 | 情绪对应颜色，全曲一致，音乐图同步 |
| 动画 | 不做无意义的时序放大缩小和闪烁 |
| 当前情绪 | 当前音乐情绪对应的组和词亮起，并随起音变化 |
| 局部小节 | 只在原稿指定的小节出现 |
| 高音等局部声音 | 对应正确的小节和音区，不能标错 |

**怎么卡**

硬门槛：

- bars 对不上；
- 高音标错；
- 无依据地给珠子添加局部位置；
- 情绪颜色前后不一致；

- 动画制造了错误的阅读时序。

美观偏好可以记录，不必每个细节都做硬门槛。

**怎么校准**

人为制作错误版本：

- 把局部小节整体错后一段；
- 把高音框标在错误音区；
- 同一情绪前后用不同颜色；
- 随机闪烁；
- 所有珠子都加底色。

评委必须能抓出来。

注意：这项必须看最终视频和实际音符数据，不能只看 JSON。

## P1-10：重建盲比基准、快筛和噪声处理

这一项解决迭代函数本身的可靠性。

### 盲比的 24 次判断

现在的做法有值得保留的地方：

- GPT-6、GPT-5.6；
- 多次重复；
- 两种版本顺序；
- 五个独立维度；
- 每首单独验收。

这些设计方向是对的。

但有两个问题。

第一，24 次判断不等于 24 个独立样本。相同模型、相同提示词的多次判断存在相关性。

第二：

> 稳定选旧必须为 0。

这个条件过于敏感。

如果有一次判断因为随机波动选了旧版，并不能直接证明新版退步。

### 建议修改

保留配对盲比，但分开报告：

- GPT-6 的判断；
- GPT-5.6 的判断；
- 两种顺序的判断；
- 各次重复的判断；
- 五个分项的胜、负、平。

不能只看总票数。

另外增加两种校准实验：

**A/A：同一版本和自己比较。**

把同一份内容伪装成 X、Y，交换顺序，让评委判断。

目的是知道：评委自己会产生多少随机偏好。

**A/B：已知有明显差异的版本比较。**

比如：

- 一个版本保留疑问，一个版本改成断言；
- 一个版本保留核心，一个版本丢失核心；
- 一个版本人话，一个版本书面化；
- 一个版本珠线混合，一个版本明确分开。

评委必须分得出来。

### 门槛怎么改

不要再使用简单的：

新版赢票不低于旧版，且旧版胜出次数必须为零。

应该使用经过 A/A 校准的非劣效区间：

- 明显且重复出现的退步：不通过；
- 在评委随机噪声范围内：不确定；
- 明确优于正例锚点：通过。

门槛边上的结果不能强行判通过，也不能因为一两票波动就立刻改提示词。

### 两首同过

这个要求应该保留：

- 两首使用同一套提示词；
- 同样的评审步骤；
- 每首独立通过；
- 不能一首的好成绩补另一首的失败。

另外，两首同过是泛化测试的必要条件，但还不能证明对任何作品都泛化。

要确保提示词不含特定作品内容。

# 六、你写的“揉在一起”提示词，具体应该改什么？

我认为方向是对的，但现在这份提示词还有几个重要问题。

最重要的是：

**它允许珠子和线使用不同的显示形态，却没有从根本上消除按来源分组的组织方式。**

而且 RHP 目前的实际结果已经证明了这一点。

## 1. 第一处：重新定义珠子和线

你现在写：

> 线：一个人经历的一件事。
>
> 珠子：听的人此刻心里和身上的感受。

这个定义作为材料说明没问题。

但需要补充：

**珠子和线只是内部的内容来源，不是屏幕上的两种栏目，也不是两种固定的文字形式。**

建议增加：

```text
线和珠子是原稿的两种内容来源，仅用于内部溯源。

屏幕上不出现“话”“感受”“线”“珠子”等来源标签。
不得按照内容来源分栏、分区或交替排版。

一个视觉组可以同时包含叙事内容和具体感受。
叙事内容可以拆成散落短语。
具体感受也可以融入连贯的话中。

内容来源与显示形式是两个独立维度。
不要因为某句话来自线，就必须写成完整句子；
不要因为某个内容来自珠子，就必须写成小字短语。
```

这是这份提示词最重要的一处修改。

## 2. 第二处：不能强制每条线都是一个完整因果句

现在写：

> 原因和它带出的结果放在同一句里。
>
> 一句连贯的话一个因果，最多两个逗号。

这实际上又把模型推回了完整句子。

而且有一个更危险的问题：并不是每个内容都存在明确因果。

你们之前已经明确指出，同段的很多线是共同描述一个状态，而不是时间顺序。

建议改成：

```text
只保留原稿明确表达的因果、转折和条件关系。

原稿存在明确因果时，应尽量让原因和结果在扫读时容易联系起来。
原稿是并列、共同描述、同时存在的内容时，保持并列。
不要为了让文字连贯而添加“所以”“于是”“随后”等原稿没有的关系。

线可以写成完整句，也可以拆成短语。
是否拆分，取决于扫读效果、独立理解能力和因果关系是否保留。
不要求每条线都是完整陈述句。
```

这也落实了 11-05 后来提出的：

> 线如果碎裂更好也可以碎裂。

## 3. 第三处：珠子不应该强制每颗出现

现在写：

> 每颗珠子至少要在屏幕上出现一次，具体的东西尽量都留住。

我建议删掉第一句。

因为它与用户已经确立的目标有冲突：

- 覆盖需要测；
- 具体体验要尽可能保留；
- 核心内容不能丢；
- 但不是每颗珠子都必须出现。

否则模型很可能为了覆盖率牺牲扫读。

改成：

```text
优先保留独立排序中最核心、最有辨识度的具体感受。

拆解珠子时，尽量保留身体感觉、具体画面、比喻和心里话。
不要把具体体验概括成泛泛的情绪词。

但不要求每颗珠子都必须出现。
允许为了扫读舍弃低优先级、重复或贡献较小的内容。

覆盖率由独立评审检查，不要为了完成覆盖清单而堆字。
```

## 4. 第四处：删掉 w23 字数比例限制

现在写：

> 每段总字数不超过参照的 1.1 倍，短段不超过参照。

建议全部删除。

原因有两个：

第一，w23 本身不是合格目标。

第二，用户已经否定过固定数值标准。

尤其不能让一个已经有问题的旧版本，继续决定新版本能写多少字。

应该改成：

```text
内容密度根据实际停留时间、扫读测试和关键信息的可获取程度调整。

不要为了满足字数比例而删掉关键内容。
也不要为了覆盖所有原稿而堆积文字。

最终以真实视频播放时，观众是否能扫到主要信息为准。
```

同样建议把以下几个固定数字从生成硬约束中移除，交给实验校准：

- 每块 3–8 个字；
- 每句 1–2 个关键词；
- 最多两个逗号；
- 25 秒以下使用另一套字数限制。

这些可以作为某轮实验的初始参数，但不能当成永远正确的规则。

## 5. 第五处：把人话标准改正确

现在写：

> 人称和称呼不变（“他”和“对方”）。

这一句应该删掉。

用户已经明确说过人称不是指标。

而且你们要泛化到不同作品，不能固定人物指代。

改成：

```text
沿用原稿实际的人物指代和称呼，不擅自改变人物关系。

人称本身不作为质量指标。

重点是句式自然、表达直接、句式多变。
允许短语、感叹、问句和不完整陈述句。
但不能把自然语言硬切成书面提纲。
```

## 6. 第六处：增加 Center 和线的四项要求

你现在的提示词没有明确要求：

- 线的压缩；
- 线的异质性；
- 线的独立性；
- 线和珠子的对应；
- Center 关联；
- DFS 深入。

这些应该加进去。

建议：

```text
线的组织必须同时满足以下目的：

1. 压缩：不重复解释，保留核心因果和必要信息。
2. 异质：原稿中不同性质的内容不能被压成同一种表达。
3. 独立：每条可见的叙事内容单独看也能理解。
4. 关联：与其对应的具体感受能够自然地出现在同一个视觉组中。
5. Center：每段都服务于全曲的核心。
6. DFS：沿着核心脉络向深处推进，不在不同分支间无依据地来回跳转。

不要求每条线都写成完整句，也不要求每条线都必须独立占据一个视觉组。
```

## 7. 第七处：颜色不能只分配给连贯行

现在写：

> 每个连贯行选一个情绪色。

这个规则在混合形态下不够。

比如同一句话里可能同时有：

- 欢喜；
- 害怕；
- 孤单。

不能因为整句话选了一个颜色，就把里面不同性质的词都染成同一种颜色。

建议改成：

```text
颜色按照实际表达的情绪分配给具体的语义片段或感受组。

连贯句和散落词块都可以带有情绪颜色。
同一种情绪在全曲使用同一种颜色。
音乐图使用相同的情绪颜色体系。

同一视觉组内存在不同情绪时，不要强行使用一种颜色覆盖全部内容。
```

你现在的情绪词列表也不应该直接作为所有作品的固定封闭集合。

应该由模型结合原稿识别情绪类别，再由颜色映射规则保证全曲一致。

## 8. 第八处：局部小节需要支持句子内部的局部内容

现在 `bars` 放在散落短语上。

但珠子和线混合后，可能出现：

一整句话只有其中一个短语属于某几小节。

如果 bars 只能挂在整行或者散落词块上，就无法准确控制。

应该让每个文字片段独立拥有：

- 来源 ID；
- 情绪；
- 显示形态；
- 局部小节（如果有）。

只有原稿明确属于局部的内容才填 bars。

不要把所有珠子都设置成“到时出现”。

# 七、最重要的改动：JSON 结构也应该改

你现在的结构：

```json
{
  "form": "连贯",
  "text": "...",
  "keys": [],
  "emotion": "...",
  "from": []
}
```

或者：

```json
{
  "form": "散落",
  "items": []
}
```

这个结构本身就把一个视觉行限定成了两种互斥形式。

建议改成**视觉组 + 组内混合片段**。

例如：

```json
{
  "sec": "S05",
  "groups": [
    {
      "layout": "mixed",
      "read_order": 1,
      "center_relation": "推进全曲核心",
      "parts": [
        {
          "visual": "text",
          "text": "他没藏住喜欢",
          "keys": ["没藏住喜欢"],
          "emotion": "不安",
          "from": ["S05-1"],
          "bars": null
        },
        {
          "visual": "chip",
          "text": "脚下没了支撑",
          "emotion": "不安",
          "from": ["S05-B1"],
          "bars": null
        },
        {
          "visual": "text",
          "text": "等他察觉，对方已经看出来了",
          "keys": ["已经看出来了"],
          "emotion": "悬着",
          "from": ["S05-1"],
          "bars": null
        },
        {
          "visual": "chip",
          "text": "话卡在嘴边",
          "emotion": "悬着",
          "from": ["S05-B2"],
          "bars": null
        }
      ]
    }
  ]
}
```

这里只是结构示意，不是要求照抄这个内容。

几个重要区别：

- `visual` 只决定怎么显示，不决定来自线还是珠子。
- `from` 只供内部溯源，不能显示给观众。
- 一组里可以同时出现连贯文字和散落词块。
- 线的内容也可以成为小词块。
- 珠子的内容也可以融入大字句。
- `bars` 可以挂在任意局部片段上。
- `emotion` 应该属于具体片段，而不是强制属于整行。
- `read_order` 只是阅读引导，不代表内容的时间顺序。

`layout` 可以有：

- `mixed`：连贯和散落混合；
- `flow`：以连贯内容为主；
- `scatter`：以散落内容为主。

不要规定全曲必须按照某种比例交替。

**连贯和散落是可选的视觉组织方式，不是内容来源的分类。**

# 八、RHP 现在具体错在哪里？

直接看 S04–S06。

<badge color="danger">目前不符合 11-08 的要求</badge>

RHP 的形式仍然是：

```text
话：熟悉的相处又让他欢喜……

感受：熟悉的歌声回来 / 呼吸挨着 / 水面光斑……

话：他几乎想把藏着的话全说出来……

感受：最后一道金光 / 亮得刺眼 / 喉咙发颤……
```

这仍然是：

- 一组叙事内容；
- 一组感受内容；
- 再一组叙事内容；
- 再一组感受内容。

即使每组内部有多个词，也没有解决来源分离的问题。

## 我认为正确的形态应该是什么？

以 S05 为例。

原稿里有：

- 他没藏住喜欢；
- 对方已经看出他有多在乎；
- 他拿不准怎么相处；
- 脚下没了支撑；
- 雾里看不清；
- 话卡在嘴边；
- 这幸福是真的吗？

这些内容应该在同一个视觉组织里共同出现。

例如，可以有这样一种组合：

    <row align="center" wrap="wrap">
      <title size="xl" color="default">没藏住喜欢</title>
      <text color="secondary" size="sm">他这次没有藏住心意</text>
    </row>
    <row wrap="wrap" gap={2}>
      <badge color="warning" size="lg">脚下没了支撑</badge>
      <badge color="warning">雾里看不清</badge>
    </row>
  </box>
  <divider color="subtle"/>

    <row wrap="wrap" gap={2}>

    <text color="secondary" size="sm">连怎么相处都拿不准</text>

重点不是一定要这样排，而是：

1. 叙事关键词可以成为视觉锚点。
2. 具体感受围绕它们散落。
3. 有些感受可以直接融入连贯句。
4. 有些线的内容也可以拆成关键词。
5. 不需要观众知道什么是珠子、什么是线。
6. 观众能自然感到：这些感觉就是这个人此刻的处境。

而且，**不要把整个段落变成一篇长文章。**

可以有一条连贯的主干，同时让其他内容散落在旁边。也可以有一组主要由散落词构成，但其中包含叙事关键词。

这才是 11-08 的意思。

另一个重要细节：

你们 11-05 已经确定的动画方式仍然应该保留：

- 非局部内容一直在；
- 当前音乐情绪对应的词和组亮起；
- 随起音跳动；
- 局部内容到指定小节才出现；
- 对应音区同色框亮起。

不能把所有珠子重新做成逐个出现的时序动画。

# 九、整个迭代流程应该怎么改？

我建议重建成以下流程。

<box border radius="lg" padding={3} gap={3}>
  <title size="lg">建议的新迭代函数</title>
  <list connector="solid" marker="number" gap={3}>
    <list-item>
      **原稿独立标注**

      对珠子+线做内容拆解、核心排序、Center 关联、DFS 路径、珠子匹配、局部小节标记。
    </list-item>
    <list-item>
      **生成屏幕稿**

      两首曲子用完全相同的写稿提示词，不注入作品特定规则。
    </list-item>
    <list-item>
      **机械快筛**

      检查 JSON、来源 ID、缺失字段、bars 合法性、无依据的局部标记等。
    </list-item>
    <list-item>
      **忠实性与核心快筛**

      先检查新增内容、疑问变断言、语气改变、核心点遗漏。任何严重问题直接退回。
    </list-item>
    <list-item>
      **内容质量完整评审**

      珠子覆盖、精细体验、线的四项指标、Center/DFS、人话、并列与因果关系。
    </list-item>
    <list-item>
      **真实扫读盲测**

      用实际停留时间、实际视频和音乐测试扫读、抓重点、知道为什么。
    </list-item>
    <list-item>
      **渲染和视听验收**

      检查融合布局、阅读路径、情绪颜色、音乐图对应、局部动画。
    </list-item>
    <list-item>
      **两首分别验收**

      每首独立通过，不允许相互补分。
    </list-item>
    <list-item>
      **历史盲比和噪声复核**

      与 w23 进行历史回归比较，同时使用人工认可的正例和负例校准评委。
    </list-item>
  </list>
</box>

## 快筛应该改什么？

现在：

> 先跑 1 和 5，过了再跑全套。

这个不够。

因为 1 是相对 w23 的盲比，5 是线人话。

一个版本完全可能：

- 很好读；
- 很像人话；
- 但核心内容丢了；
- 甚至新增了原稿没有的事实。

所以快筛至少应该有：

| 快筛项目 | 目的 |
|---|---|
| 机械结构检查 | 防止来源和局部小节信息丢失 |
| 事实忠实性 | 防止新增、改变语气、制造因果 |
| 核心覆盖 | 防止最重要的内容丢失 |
| 初步扫读 | 防止明显超载或过度压缩 |

这些通过以后，再跑完整评审。

## 每首 24 次判断应该怎么改？

我建议保留重复判断，但不要把 24 次看成 24 个完全独立的证据。

每次都记录：

- 模型；
- 版本顺序；
- 重复组；
- 具体分项；
- 判断理由；
- 是否出现实际回归。

另外增加 A/A 和正反对照。

## 门槛边上的噪声怎么处理？

op60 在“知道为什么”和“扫得动”之间一两票来回，这不是继续修改内容的充分理由。

建议给每个指标设置三种状态：

<row align="center" gap={2}>
  <badge color="success">通过</badge>
  明显达到要求，且没有实质性退步。
</row>
<row align="center" gap={2}>
  <badge color="warning">待定</badge>
  结果落在评委自身的噪声区间内。
</row>
<row align="center" gap={2}>
  <badge color="danger">失败</badge>
  有可重复、可定位的实质性问题。
</row>

处于待定时：

1. 冻结当前版本，不要立刻修改。
2. 重新进行独立一批盲评。
3. 检查是否为模型、顺序或随机波动。
4. 如果仍无法区分，让人工对照具体片段裁决。
5. 只有确认问题以后才修改。

尤其不能因为某一轮 scan 少一票，就为了提高 scan 分数删掉重要内容。

**任何硬门槛都不能被其他指标的高分抵消。**

# 十、最后给出我建议采用的目标函数

不要再把它理解为一个单一分数。

它应该是一个多目标约束系统。

可以概括为：

\[
\text{通过}
=
\text{忠实性}
\land
\text{核心保留}
\land
\text{真实扫读}
\land
\text{珠子质量}
\land
\text{线质量}
\land
\text{叙事结构}
\land
\text{视听对应}
\]

其中：

| 目标 | 性质 | 是否允许其他分数补偿 |
|---|---|---|
| 不编、不改变原意 | 红线 | 不允许 |
| 核心内容保留 | 红线 | 不允许 |
| 真实扫读 | 硬门槛 | 不允许用覆盖率补偿 |
| 珠子具体体验 | 独立门槛 | 不允许用线的内容补偿 |
| 线压缩、异质、独立、关联 | 四项独立门槛 | 不允许互相补偿 |
| Center、DFS | 硬门槛 | 不允许 |
| 人话 | 硬门槛 | 不允许 |
| 珠线融合、阅读路径 | 硬门槛 | 不允许 |
| 视觉、动画、音乐对应 | 硬门槛 | 不允许 |
| 低优先级内容覆盖 | 优化目标 | 可以放宽 |
| w23 历史盲比 | 回归监测 | 不能决定合格 |

## 我的实际执行建议

不要同时修改所有东西。按照这个顺序：

**第一轮：先修评审体系。**

1. w23 降级为历史参照。
2. 增加忠实性硬门槛。
3. 增加独立核心排序。
4. 修正珠子覆盖评审，不再只看小字。
5. 增加线四项直接评审。
6. 增加 Center/DFS 评审。

**第二轮：修写稿提示词。**

1. 删除来源分行逻辑。
2. 支持混合视觉组。
3. 不强制完整因果句。
4. 不强制每颗珠子出现。
5. 删除 w23 字数比例。
6. 删除固定人称和固定情绪集合。
7. 加入 Center/DFS 和线的四项要求。

**第三轮：端到端测试。**

1. 先用 Op.52 跑完整流程。
2. 再用另一首完全相同的提示词跑。
3. 两首分别验收。
4. 真实视频盲测。
5. 最终渲染验收。

**最后的判断：你们现在最大的问题不是模型写得不好，而是评审函数没有把你们真正关心的东西变成可靠的、能够区分正反例的门槛。**

尤其要注意三件事：

- 一个不合格的 w23，不能定义什么叫合格。
- 一个很会写人话的模型，不代表它忠实于原稿。
- 一个文字盲比表现很好的版本，不代表它真的能在视频里被扫懂。

这三个问题不解决，继续跑几百轮迭代也可能只是越来越擅长满足错误的评审标准。

我建议先冻结当前 RHP 写稿实验，完成上面 P0 的六项评审修复，再开始下一轮。
