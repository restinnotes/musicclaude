# 直接执行任务：用 `gpt3` / GPT-6 Max 自进化 Thread 生成提示词

你是被授权自主进行实验的本地 Agent。你需要**真正执行模型调用和实验**，产出被实证检验过的「通用 Thread Prompt + 精简材料协议」，而不只是写实验规划或优化某篇《船歌》文章。

## 0. 你的最终目标和操作权限

从《船歌》GPT-6 Max 一次生成的较强样本出发，**发现一套可在其他古典音乐作品上复用、能稳定生成高质量 Thread 的提示词和输入方法**。对某一篇文章的逐句打磨，不能算提示词进步。你有权自由设计生成、评价、选择、变异、重新采样和停止机制（例如多个候选提示词并行、失败驱动改写、盲评、正交消融、先诊断后改动）；不需要遵循任何既有 Bead→Thread→Inner→Outer 生产 DAG。

你拥有完整的提示词 P0、原先的 B0 一次性输出，以及 14 段 reader、51 条 Bead 等独立输入版本。**不要索要一个人为你制定的具体工作流；你自己决策和执行。** 但必须满足以下可检验边界。

## 1. 真正使用的模型和接口：本地 `gpt3` CLI

`gpt3` 是**终端命令**，其内部可以选择/调用 GPT-6 Max；它不是模型名字，不是这个对话的“GPT-3”模型，也不是让你调用一个叫 gpt3 的子智能体。

- 首先在你的实际执行终端检查 `gpt3` 是否可运行。例如在 shell 中 `command -v gpt3`、`gpt3 --help`；PowerShell 可使用 `Get-Command gpt3`、`gpt3 --help`。如果它是 wrapper、交互菜单或 shell alias，自行探查帮助、命令来源及正确的非交互调用方式。
- 从真实帮助或实测界面发现 GPT-6 Max 的实际模型标识、指定模型的方法、如何向模型提交文本、如何抓取输出、是否支持非交互模式、是否支持设置 thinking/采样参数。
- **必须通过 `gpt3` 命令真正调用该模型**。可以编写脚本自动化它，前提是最终模型推理仍经 `gpt3` 命令完成。不要擅自替换为 OpenAI API、其他 GPT 模型、Codex、OpenCode 或任一便宜模型，也不要假定 `gpt3 --model`/`-m` 必然存在。
- 至少保存一次小型探测调用的原始 stdout/stderr、退出码、实际命令和模型证据。若该入口不可用，在报告中明确阻塞，保留实验设计及可用材料，但**不能把模拟输出算作实验**。
- 本打包环境未验证本机 `gpt3` 的命令行约定，因此不附会任何虚构参数。

## 2. 冻结第一轮的事实基线

必读：`01_提示词与基准/P0_纯提示词_直接调用.txt`、`01_提示词与基准/B0_成功范例_水面从来不答应静止.md`。

- P0 是用户粘贴的成功提示词；不要在第一次对照运行之前擅自修改它。此前旧版打包的 P0 是「规范化复写」，本包重新按用户提供的正文保存。可进一步回查 gpt3 原会话以精确验证；如存在差异，记录差异，并同时保留原包 P0。
- B0 是用户认为明显胜过此前迭代稿的**一次生成结果**，不是证明该 Prompt 稳定优秀的重复实验。B0 本身并非无错：误将分段边界 117 理解为附加小节；有部分音乐事实和人物心理跃迁待核验。
- B0 只供独立评审理解质量标杆，**默认不传给负责生成候选的 GPT-6 Max**。不同的解释主线、写法、长度可以胜出，绝不可把“越像 B0、越像幸福与时间”当评分目标。

## 3. 两条 Bead 路线必须亲自测试，不能靠直觉决策

固定 P0、固定模型/配置，对以下至少三组进行**真正的从零调用**，每组建议至少重复 3 次以识别样本随机性。实际调用不足则在报告中说明，不要报出没有跑过的胜率。

| 必测条件 | 生成输入 | 检验问题 |
|---|---|---|
| D0 | **P0，无附加 Bead** | 成功原版是否可复现？ |
| D3 | **P0 + 14 段正式 reader** | 精简的局部体验是否让整体 Thread 更准确、更鲜活？ |
| D4 | **P0 + 全部 51 条 Bead 的正式文字** | 更丰富的局部观点是否带来净增益，还是导致重复、喧宾夺主或强行串接？ |

**D3 与 D4 的正面比较是硬要求，不能把某一档设为 optional。** 这里“14段”不是“51条的前14条”：D3 是14份综合正文；D4 是分属14段的51条独立体验，可能兼容，也可能互相竞争。

另有 D1（每段音乐锚点）及 D2（每段 B1 主体验）两种中间输入。可以自由设计何时测、要不要产生新的 D5/D6（例如只选关键位置、剥掉解释仅留事件、自动筛选最佳1–2条/段、按主题适配），但必须**把 D3 vs D4 作为实际检验对象**。你应该尤其测试：主干先由模型自主发现、Bead 后用于修正；和从一开始读取 Bead；这两种入口是否改变质量。不要把“使用 Bead”偷换成“最终逐字粘贴 Bead”。

比较时避免同时改动 Prompt 和 Bead 输入，除非你另设了可分辨交互效应的对照。D3/D4 当前前言、标题也可能影响结果，必要时设计**等格式**的输入协议，以免把包装差异误当信息量差异。

## 4. 提示词自进化：要求真正迭代 Prompt，不是文章

完成一轮基线比较后，你自主选择最有希望的方向，生成若干新的 Prompt 候选（P1、P2……）：

- 发现文章的**具体失败机制**，并据此提出修改，而不是机械向 P0 追加一长串禁令。
- 在真实模型输出里验证修改是否有效；每一份候选文章必须是从头生成，而非在 B0 或之前成品上修段落。
- 允许开发 Prompt 自变异+自主裁判循环，允许拆分「发现多个可能的全曲关系」与「展开全文」两个内部阶段，也允许证明最简单的单次 Prompt 最好。
- 保留优秀但不同的结果，不因为不同于 B0 的哲学主张或场景而丢掉；发现新的优良生成策略后，反过来检验它是否仍需要 Bead。
- 不要被「每段都要有新认识」「每段都必须回指」等表格绑架；当前有些时刻应充分停留，真正的纵向作用可以在更后面显现。
- 修改的目标是生成规则、材料筛选与组织方式，不是强制某篇文章“再写得漂亮一点”。

算法/机制由你自行发明，允许超出前述建议。研究成本并非本项目首要因素；把实验次数花在能辨别质量差异的地方，而不是无穷重试直到碰巧得到一篇漂亮稿。

## 5. 如何判断 Thread 真正进步

先将小节、提示词来源、材料标签匿名，**整篇一口气读**。检查这篇文章即使不看 Bead/脚注，是否有读者值得跟着经历的一件事，是否前面真正建立过的东西在后面起作用，人物/听者的情感是否经历了具体、不是宣告式的改变。读完应能指出：究竟是什么在变、为什么、保留了哪些尚未解决的东西，而不只是“越来越激动”。

具体拒绝以下假阳性：
1. 只是“温柔→不安→高潮→释然”情绪顺序表，或者每段再附一行“因为前面所以现在”。
2. 一套中心哲学结论先行，每段都被写成证明它的例子；结尾强行人生顿悟或解决此前根本没有建立的问题。
3. 用“承托/失重/敞开/更有分量/终于”等抽象运动词代替可进入的人类处境与真正的理由；文字注水、逻辑兜圈。
4. 将互不相容的 Bead 替代读法拼成同一个人经历的连续事件；为故事方便虚构音乐事实，漏掉真正特殊的当下体验。
5. 为了引用更多 Bead 而变得更像音响描写合集，损害了文章独立可读的 Thread。
6. 过度刻意追求旧样文的“航行—安稳—放手”主题，丧失跨作品能力。

积极识别：体验内容逐渐积累，前文的具体满足和失败改变后文的所求；同一音乐回归因为经历不同而产生新的情绪；新的需要既有实际来历，也允许不被结尾回答；读者能具体感到而非只接受作者的宣告。Center/History/Connection/Inner/Outer 是思考工具，不是读者必须看到的栏目。

**文学可读性**与**音乐可核查性**必须分别验收。音乐事实不宜完全依赖 B0 的技术描述；针对关键转折有条件查乐谱/权威研究、记下可检查的位置。评审不能只问“全文感人吗”，也不能只问“资料对齐率多少”。

建议采用独立/盲审；如只用 GPT-6 Max 自审，需明确标记存在同模型偏好和过拟合的局限。保留两个以上不同候选及反例，而非只展示自己选出的最佳样本。若模型不支持稳定 seed，就重复采样，记录这种限制。

## 6. 泛化与停机

你需要选至少一个**没有参与调整 Prompt 的新作品**（例如肖邦 Op.61，或另一个能获得可靠分段/音乐依据的作品），开展持出测试，至少比较 P0、当前胜出 Prompt 的同等条件输出。不要把 Op.60 的“幸福”“水面”“恋人”“时间不能停”等内容写入通用提示词。若没有另一首作品的可靠分段/材料，可先在同作品开展研发，但最终报告必须明确标注「泛化尚未验证」，不得声称已得到通用最优方案。

你自行制定合理停止条件：看边际质量改进、稳定性、输入信息量和泛化能力；变长、变复杂不意味着更好。若发现原始 P0 最好，也应该如实保留这个结论。

## 7. 交付与可复现性

在你自己的运行目录中保存全部实际的：`runs/<run-id>/prompt.txt`、`input.txt`、`output.txt`、`call.log`（命令、模型选择、耗时、退出码，隐藏凭证）；`prompt_versions/P0,P1...`；`evaluations/`；`FINAL_PROMPT.txt`；`FINAL_INPUT_PROTOCOL.md`；`FINAL_REPORT.md`。

最终报告必须说明：

- 使用的**真实 `gpt3` 命令**及 GPT-6 Max 模型识别证据；是否实测成功；
- D0、D3、D4 的实测差异（D1/D2 如果实验过也纳入）；重复样本的起伏及至少一例失败；
- 具体修改了哪些 Prompt、为什么修改、如何证明发生了进步或退步；
- 最佳可直接复制的通用 Prompt 全文和最佳精简 Bead 组织规格；
- 最优输出与 P0 原版的盲评、音乐核对、至少一次持出作品测试或明确的缺口；
- 你自己最终愿意推荐的机制，不因本说明文档预设某套固定 pipeline。

**请开始实际操作：先检查 `gpt3`，读完材料，开展第一组实测，然后自行进入迭代，不需要先只把计划复述给用户。**
