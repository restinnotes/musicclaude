# 开发规范：怎么避免越做越晕

由来：10-29 到 11-01 三天里压缩了 8 次，出现过这些问题：同时修两条底稿不同的线，然后拿它们互相比；成品漂到了不是 DAG 产出的线上；重建写稿层时丢了 10-23 的修正；把没校准过的分数当证据；实验输入没读进去就白跑；没测完就打包交付；结论先说出口、后来又改口。下面每一条都对着其中一个毛病。

## 1. 四份文件，各管一件事

| 文件 | 管什么 | 什么时候改 |
|---|---|---|
| `标准.md` | 用户要什么（11-02 按时间重整，带原话；只有用户能改） | 用户提出新要求时 |
| `THREAD_SPEC.md` | 历史档案，查来龙去脉用，不再喂给模型 | 不再更新 |
| `DAG.md` | 怎么生产（节点、提示词、状态、修订记录） | 任何流程、提示词、模型变化时；改完跑 `python dag_export.py` |
| `STATUS.md` | 现在在哪（主线版本、做好了什么、问题、下一步、在跑什么） | 每做完一步就**覆盖更新** |
| `VERSIONS.md` | 每个版本的来历和测量 | `python versions.py` 重建 |
| `用户判定.md` | 用户对每个版本的评判原话 | 用户每评一次就记 |
| `迭代准则.md` | 怎么试、怎么评（快筛 / 合并跑 / 验收、检查点、评审工具）；提示词原文 `python exp_export.py` → `迭代准则_评审提示词.md` | 改评审方法或评审提示词时 |

接续工作或压缩之后，先读 `STATUS.md`。结论要写进文件，不能只留在对话里。

## 2. 只有一条主线

- 主线就是 DAG 端到端的产物，成品只从主线出。
- 实验从主线的某个版本出发，**只改一处**。动手前写下三件事：假设是什么、改了什么、期望看到什么。
- 实验通过验收 → 写进 `DAG.md`，主线前进；没通过 → 在 `DAG.md` 修订记录里记一行结论，然后放弃。
- 不另起一条"看起来更好"的线去修补（h 线就是教训）。
- 只有上游层（N04、N05、N06）改了，才从那一层往下重跑；否则就在主线现有产物上往下改。
- 版本的 base 字段要写清改了什么，不要只写"通用流程"。

## 3. 改一层之前

- **先改已有的提示词，再考虑加层**（用户 11-01）：开放评审挑出的问题，先归纳成通用问题，回去改产生它的那一层（越靠前越好）；改不动才加新层。层数膨胀会难调试。

- 先在 `THREAD_SPEC.md` 和 `DAG.md` 修订记录里搜这一层以前有过的发现。
- 提示词里不放这两首作品的例子，也不手写只针对一首的说明。发现的问题要变成通用步骤加评判，两首作品走同一流程。

## 4. 怎么评、怎么迭代（11-01 定）

**三类测量，各有各的用处**

| 用途 | 测量 | 怎么用 |
|---|---|---|
| 守底线（不许变差） | 覆盖 `v6cov`（逐颗珠子，两位评委）、单独读 `v6alone` | 已经接近满分，只看有没有掉：任何一段两位评委都掉 2 分以上、或单独读少成立一段，就不收 |
| 判断有没有变好 | 新旧两版盲比 `v6fix blind`，2 首 × 2 位评委 × 2 次 = 8 份 | 主要看小数点那几个数：每份里逐段在 覆盖 / 啰嗦 / 人话 三项投给一边，“新版赢的段数 − 旧版赢的段数”取 8 份平均（如 人话 +8.6）；再看 选新版几份、判不算退步几份、平均丢了几条 |
| 找问题（不打分） | 四维开放评审 `e2e_open`（11-01 起为主；先只读线看单独成立/啰嗦/人话，再对照珠子看接不接得上）；语言开放评审 `lang_open` | 只用它列出的问题来决定改哪里，不打分 |

**收下一个改动的标准**：底线没掉；盲比 8 份里至少 6 份选新版；人话、啰嗦净胜都不为负；至少 6 份判不算退步。

**迭代循环（11-02 改：用户要大改、要快）**
- 每轮先请多位顾问（GPT-6 ×2、5.6、Gemini 3.8、Argon）看整条流水线的提示词 + 各层产物 + 四维开放评审的问题 + 用户判定 + 用户认可过的对照版，诊断哪层哪句造成问题、给大改方案（可删层并层、整层重写）和没试过的办法（`prompt_advisor.py`）。
- 我综合成 2–3 个差别大的方案同时跑；先短跑到出线 + 测覆盖，用四维开放评审和盲比筛；赢的再跑全流程做正式验收。
- 不再一次只动一句；"只改一处"只用于正式验收时的对照。

旧的循环（仍适用于正式验收）：
1. 基线 = 现在 `DAG.md` 里的流水线原样跑一遍、测完（就是 e 线跑完）。
2. 开放评审读基线 → 把问题归纳成通用问题 → 找出是哪一层的提示词造成的 → 只改那一处 → 从那一层往下重跑。
3. 按上面的标准和当前主线比。过了，主线换成新版、写进 `DAG.md`；没过，记一行结论、放弃。
4. 几个改动可以同时试，各自都和同一个主线比；都过了再合在一起比一次。
5. 到了阶段节点再给用户看。用户的判断原话记进 `用户判定.md`；用户和评委意见不一致时，以用户为准，并回头调评委。
6. 超没超过 h23，只在阶段节点盲比一次看差距，不用来决定改哪里。

- 新评委、新指标要先校准：能抓出用户指出过的问题句、能复现用户的判断，才算数。
- 只比只差一处的两个版本；评委换了路由，先在同一路由下重测旧版。
- 需要时再加：几个版本很接近时用分段排序 `sectour`。

## 5. 跑实验的时候

- 跑之前先核对输入确实进了提示词：打印条数，读到 0 条就停（N09d 没读到意见白跑过一次）。
- 第一个结果回来就读，不对立刻停。
- 同时最多开 2–3 个方向，每个方向在 `STATUS.md` 里占一行。
- 链的最后一步是补测：把失败的评委重跑到齐。
- 报进度或预计时间之前，先看最近有没有新的输出文件。
- 并发不超过 10。遇到保护信号就停下，告诉用户，等用户换账号。

## 6. 汇报

- 只报测到的结果；是猜测就说"我猜"。
- 说结论之前先核对原始结果，避免说完再改口。
- 没测完就说"做了一半，还缺什么"，不打包、不交付。
- 交给用户的是成品（只看线、合写各一份），标明版本名，不匿名；中间产物不让用户读。
- 只在关键事件时通知：失败、完成、结论。

## 7. 自己推进

- 标准已经有了（`THREAD_SPEC.md` 加上第 4 节的验收），按标准自己判断，不等用户决定。
- 只有真正属于用户的决定才问：口味上的新标准、硬约束冲突、账号问题。

## 8. 不用 git

用户 11-01：没必要用 git，配 worktree 麻烦。并行时每个方向用自己的版本名；要改提示词就复制一份单独改。派给 Codex 的活写清楚范围，只让它动自己那几个文件。找回旧提示词靠 `runs/<编号>/prompt.txt`（每次调用都存了原文）。
