description: 10-21 user — assembly must not filter beads down to the line's single reading; keep bead roles (main experience, in-segment change, alternative listenings); the line must not be more certain than the original (the Center is discovered gradually)
metadata:
  type: feedback
---

User (2026-10-21), on the Op.61 1–23 product: "前面23小节你这样组织就是非常加重一个策略而忽略很多其他策略".

What went wrong:
- The beads for that segment had five listenings plus an in-segment change: summons waiting for echo; unnamed loss ("anger, regret or nostalgia?"); waking disoriented; memory scene 9–17 → steps emerging 18–23; forcing oneself upright.
- My pick/condense prompt kept only beads that "fit the line's state", so only the line's own reading survived.
- The show layer also front-loaded the Center. The original said he could not yet tell what he was holding on to; the show line said "他怕原来的世界不认他" outright.

**Why:** the line answers how far the matter has got. The beads keep the multiplicity of how this moment can be heard. Filtering beads by the line collapses that multiplicity. P0's core is that the matter is recognised gradually, so early "说不清" is content.

**How to apply:**
- Bead selection is by role: always keep the main experience; keep an in-segment change when there is one; keep at least one alternative listening, framed as "也可以听成…". Never filter beads by the line's reading. Only flag direct contradictions.
- Condensing or showing the line must never be more certain than the original. Final review checks for later recognitions placed too early.

Related: [[thread-node-no-beads]], [[thread-form-not-prose]].

########## check-runs-frequently.md
---
name: check-runs-frequently
description: "During long background runs, wake on every new result and inspect it immediately instead of waiting for the whole batch"
metadata:
  node_type: memory
  type: feedback
  originSessionId: 7c623294-a1ea-40eb-b513-ae6588ad2c39

---

User (2026-10-21): "你尽量每一次都去 check 频繁一点". They said this while graph builds took 15–20 minutes each and I was waiting for whole batches before looking.

**Why:** waiting for the whole batch hid problems that the first output already showed. For example, the v4 graph chopped every sentence into 8+ fragments, and that was visible in the first finished graph. Late checks waste a full round of GPT calls and leave the user wondering what is happening.

**How to apply:**
- Arm a waiter that exits on the *first* new event (a new result line in a log or a new output file), not on batch completion.
- Read that first result right away (view plus check numbers). If it's off, stop the batch and fix the prompt.
- Re-arm the waiter for the next event.
- Tell the user briefly what each check found.

- 10-27: user: "你应该自己来跟我说说你觉得应该怎么样……中间发现问题不去修复的话，不是会很严重地拖慢我们的进度吗". I had let P4a run
  to the end and then asked the user "finish or stop?". **Rule:** when a mid-run check shows a problem, decide myself, fix it at
  once (stop or redo only the affected step), then report what I did; don't hand the user a choice question. Also check early
  that the run's key new ingredient is actually used (P4a: D21 turns were ~40% of the pool but picked 3 times; visible after 4 segments).

Related: [[notify-only-key-events]] (still don't spam the user; checking often is about my inspection, and messages stay short).

- 10-21 incident: I launched the same run id twice, two times. Once was a manual re-run while the first call was still going. The other was a command chain that kept going after a failed patch step. The later finisher silently overwrote output.txt, and judged versions became unrecoverable from the run dir. I recovered them from the gpt3 job dirs. **Rule:** before relaunching, check running processes; give every attempt a new run tag; never put a launch on the line after a step that may fail.
