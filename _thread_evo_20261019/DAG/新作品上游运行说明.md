# 新作品上游运行说明

本说明只覆盖 N02 A 稿、N03 珠子、N04 Center。登记和渲染可以完全离线；文中标为“正式运行”的命令会调用模型，本次参数化和自测没有执行这些命令。

## 1. 登记作品和分段

在 `D:\musicclaude\_thread_evo_20261019\works\<key>\` 准备两个 UTF-8 JSON 文件：

- `work.json`：作品参数。key 只允许字母、数字、下划线、连字符。
- `segmentation.json`：已经确定的分段。沿用项目现有结构，不在这三步里重新研究或改变分段。

新作品 `work.json` 的示例（以 Op.52 为例；时长预算和分段来源必须按实际材料填写）：

```json
{
  "key": "op52",
  "composer": "肖邦",
  "title_zh": "《第四叙事曲》",
  "tonality": "f小调",
  "opus": "Op.52",
  "segmentation_source": "所选公开分析的机构／作者",
  "segmentation_source_note": "说明采用哪份资料、哪个层级及采用理由",
  "specificity_candidates": [
    "船歌 Op.60", "幻想波兰舞曲 Op.61", "第一叙事曲 Op.23", "第四叙事曲 Op.52",
    "幻想曲 Op.49", "摇篮曲 Op.57", "夜曲 Op.27-2", "夜曲 Op.48-1",
    "英雄波兰舞曲 Op.53", "第三奏鸣曲 Op.58 第三乐章"
  ],
  "specificity_right": "第四叙事曲 Op.52",
  "seconds_per_measure": 3.0,
  "fix_session": "fresh"
}
```

`title_zh` 包含书名号；N02 渲染为 `composer + title_zh + tonality + 空格 + opus`，N03/N04 渲染为 `composer + title_zh + opus`，保留旧提示词的空格用法。`segmentation_source` 填机构／作者的短名称；程序结合分段数生成“冻结十三段”“冻结的十三段”等原有句式。`segmentation_source_note` 是登记说明，不额外插入提示词。候选清单顺序原样保留，应为同作曲家的约十首作品，必须含 `specificity_right`；清单长度会同步进入专属性提示词。

`seconds_per_measure` 决定注意力预算：`round(本段小节数 × 此值)`，不是精确演奏时长。Op.60 保留 4.4、Op.61 保留 2.7，换曲时根据常见演奏时长设置。

`fix_session` 必须明确选择：

- `resume`：延续本段 gen_b 会话修订，保留 Op.60 原来的方式。
- `fresh`：新会话中给出本段 final_b 原文和 24 份原稿，再给整曲修订意见，保留 Op.61 原来的方式。

新作品不要复制旧登记里的 `bead_legacy_root`、`pool_sources`、`a_sources`、`old_center`。这些字段用于接回已有实验路径、历史 Pool 和 OLD 候选。新曲默认 A 原稿目录是 `works\<key>\A\`，珠子运行目录是 `works\<key>\bead\runs\`，A 生成目录是 `works\<key>\gen_A\`。`old_center` 可选；没有时不会引入其它作品的 OLD 句。

旧登记还保留 `a_job_suffixes`：历史 `gpt56w-int-1` 提示词比基础模板多原有的“回答时请不要进行联网搜索。”。它按任务名保存原样后缀；默认补稿任务不含这一份，不受影响。新作品可不填。可选 `a_runner_dir` 可指定已有非 GPT runner 的 tools 目录；默认复用 `music_work_since_1008v3_20261009\tools\runner.py`。

`segmentation.json` 最小结构如下。下面三段仅示范格式，不是 Op.52 的正式分段：

```json
{
  "work": "作品完整名称",
  "short_name": "作品简称",
  "total_measures": 30,
  "boundaries": [1, 11, 21, 31],
  "segments": [
    {"id": "S01", "start": 1, "end": 10, "label": "第一段"},
    {"id": "S02", "start": 11, "end": 20, "label": "第二段"},
    {"id": "S03", "start": 21, "end": 30, "label": "第三段"}
  ],
  "source": {"note": "实际分段依据"},
  "method": "已确定的分段方法"
}
```

程序校验 S01 起连续编号、闭区间无缺口无重叠、总小节数和边界表一致；最后边界是总小节数加一。现有 Op.60/61 的标签和边界直接读取既有 `segmentation.json`，没有重新编号。

## 2. 先做离线渲染

PowerShell 5.1 读写中文时显式指定 UTF-8；推荐用 Python 的 `encoding="utf-8"`。以下命令在 PowerShell 中运行。`WORK` 是默认作品 key；每条命令也可用 `--work op52` 覆盖。`WORKS_ROOT` 是可选的登记根目录，默认 `...\works`；临时测试可指向 `_codex\param_20261101\tmp\works`，无需往正式 works 里放测试曲。

```powershell
Set-Location D:\musicclaude\_thread_evo_20261019
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:WORK = 'op52'
$preview = 'D:\musicclaude\_thread_evo_20261019\_codex\param_20261101\tmp\my_preview'
python ..\_bead_op61_20261020\gen_A\gen.py --work op52 --corpus24 --render-dir "$preview\N02"
python center_from_A.py --work op52 --render-dir "$preview\N04a"
```

N02 输出两份提示词和包含 24 个任务的 `jobs24.json`，不导入非 GPT runner，不提交任务。N04a 只渲染文章归纳提示词，不要求 A 稿已经生成。

N03 的完整后续提示词包含此前各步的模型内容，因此离线重放还需要历史结果或明确准备的测试夹具。`--history-root` 下应包含：`pool_v2\pool\Sxx.parsed.json`、`gen_b\Sxx.parsed.json`、`rev1_b\Sxx.parsed.json`、`rev2_b\Sxx.parsed.json`、`final_b\Sxx.parsed.json`、`piece_b\ALL.parsed.json`；可选各阶段 `.meta.json` 提供历史 session_handle。无需伪造模型结果；没有这些内容时，可以先检查参数模板，等真实阶段产物齐备后重放完整输入。

```powershell
python ..\_bead_op61_20261020\chain.py render --work op52 --history-root '历史或测试的 runs 目录' --render-dir "$preview\N03"
```

该入口只捕获渲染结果，不创建 sources.zip、不发送请求、不保存任何模型结果。输出 pool、gen_b、rev1_b、rev2_b、final_b、piece_b、final2_b 和逐段结构规范。整曲 piece 始终读取全部分段的 final_b；`--segs` 仅缩小逐段输出范围，不改变整曲材料。

N04b/c/d 可读取正式 A 归纳和 Center 结果，也可显式提供临时 JSON：

```powershell
$env:CDV = '2'
python center_dag.py render --work op52 --a-json '临时归纳.json' --candidates-json '临时候选.json' --render-dir "$preview\N04"
```

归纳 JSON 含 `per_draft: [{"core": "…"}]` 和 `clusters: [{"n": 24, "summary": "…"}]`；候选 JSON 是 `[{"id": "N1", "center": "…"}]`。不传这两个参数时读 `evaluations\centers\A_<key>.json` 和 `cdw<CDV>_<key>` 的结果。`render` 与正式运行使用相同的洗牌种子：专属性每位评委两次，解释力每位评委一次。默认输出包含现有调用层的 NO_WEB 后缀；`--raw` 输出进入调用层前的正文。N04a 离线输出为历史实发 cA 的原始正文；当前发送层仍可能加 NO_WEB，行为由未修改的 evo／调用模块决定。

所有离线输出使用独占创建：目录中已有同名文件即报错，换一个新的预览目录即可，勿指向历史 runs 或 DAG 快照目录。gpt3 CLI 原有行为会统一换行并 `rstrip()`；对照其服务侧 `prompt.txt` 时应重放这一处理，对照脚本层的提示词则保留末尾换行。

## 3. 正式运行顺序（会调用模型，本次未执行）

先完成 N02，取得 24 份 A 稿；然后 N03 珠子与 N04 Center 可分别运行。

```powershell
Set-Location D:\musicclaude\_thread_evo_20261019
$env:WORK = 'op52'
$env:CDV = '2'
python ..\_bead_op61_20261020\gen_A\gen.py --work op52 --corpus24
python ..\_bead_op61_20261020\chain.py production --work op52
python center_from_A.py --work op52
python center_dag.py write --work op52
python center_dag.py spec --work op52
python center_dag.py fit --work op52
python center_dag.py report --work op52
```

`--corpus24` 生成 4 模型 × int/web × 3：Gemini Flash、Luna、GPT-5.6、GPT-6。GPT 使用原 gen.py 的 gpt3 启动方式；Gemini/Luna 复用已有 runner 和其工具策略，不修改 runner 的缓存、服务或 watchdog。完成后逐字收集为 `A\SRC-<模型>-<int或web>-<1至3>.md`。A 目录已有完整同名 24 份时跳过；存在部分文件或异名文件时停止，避免覆盖已有材料。生成中途失败时保留各后端既有缓存，确认输出完整后重跑，或自行将已验证的 24 份原文收集到 A 目录。

不带 `--corpus24` 的 gen.py 仍是原来的 **10 个 GPT 补稿任务**，不是从零生成 24 份。已有外部原稿也可以直接准备 24 个 `SRC-*.md` 放入登记的 `a_sources` 目录，再从 N03/N04 开始。

`chain.py production` 在当前进程中配置并复用未修改的 sat.py 生产任务：pool → gen_b／rev1_b → rev2_b → final_b → piece_b → 只修被点名的 final2_b。保留续会话关系、sources.zip、quoted 原话核验、成功缓存、uncertain/parse_error 停止和原有并发控制。它没有增加保温任务、watchdog 或新的轮询器。需要继续使用 pool 单步入口时，可运行：

```powershell
python ..\_bead_op61_20261020\chain.py pool --work op52 --tag pool_v2 --segs all
```

最终珠子按段取 `final2_b\Sxx.parsed.json`（该段被点名且修订成功时），其余取 `final_b\Sxx.parsed.json`。`production` 到这些机器可读产物为止，不调用写死 Op.61 的 build_op61.py。原 `synth/audit/display/all/build` 是旧链实验入口，不是本说明的 N03 七步生产流程。

Center 的 A 稿归纳保存到 `evaluations\centers\A_<key>.json`；写句/解释力沿用带 key 的 run id。只测一首作品的专属性使用独立 scope（如 `cds2_op52_gpt6_1`），避免覆盖旧双作品测试的 key。`report` 给出解释力、展开空间、专属性及候选句，沿用原有实验的人工挑选方式，不新增自动阈值。

## 4. 原实验兼容性与边界

不设置 WORK、不传 --work 时，Center 仍默认同时运行 Op.60、Op.61；chain.py 和 gen.py 默认 Op.61。原 `CDV` 行为不变：DAG 的 N04b 用 `CDV=2`；不设置时仍选择原 WRITE 版本。需要原来双作品联合的专属性测试时，清除 WORK 或使用 `--work op60,op61`。联合测试要求两首登记的作曲家和候选清单完全一致，否则分别运行，不自动合并或替换候选。

centersel.py 的 SPEC、FIT、PIECES、RIGHT 导入接口对 Op.60/61 保持原值；新增 `spec_for(key)`、`fit_for(key)` 供参数化 DAG 使用。centersel 自身旧 pool 是历史研究候选比赛，仍包含旧实验来源选择；新作品从 center_dag.py 走，不需要这些历史研究文件。

原始 `*.op61.txt`、旧珠子提示词、sat.py、finish.py、build_op61.py、DAG.md 和 DAG/prompts 都保留原样；直接运行这些旧脚本仍可能固定作品。新作品使用本说明列出的参数入口，不直接运行旧 sat.py／finish.py／build_op61.py，也不运行会重建 DAG 快照的 dag_export.py。
